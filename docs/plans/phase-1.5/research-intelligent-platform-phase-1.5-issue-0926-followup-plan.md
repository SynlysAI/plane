## 1. 复核在对齐什么

第一轮把 0926 收成 14 个编号，并按 A–G 写了完成门槛。2026-09-27 人工复核不是另一批需求，而是用同一批页面判断这些门槛有没有在正在使用的 `public` 库里发生。

对齐结果：

- 已关闭 3 项：系统管理整页崩溃、新建项目不再默认旧流程、主 PI 不再落进假失败的私有工作区。
- 部分关闭 3 项：平台配置密度、集成阶段文案、周报重复追加。现场剩下的是另一层症状。
- 未关闭 8 项：管理端登录后停在标志、工作项下拉、节点信息架构、实验空态、器件库、总览人名与行数、组织层级，以及集成连接本身。
- 新增 1 项：直接导师、向上 PI、主 PI 能看见学生课题，看不见对应 Plane 项目。
- 报告与成果只看到表单和空列表，上传还没被证明，先保持待复核。

第一轮实施状态把「代码已提交」写成了「已落地」。复核时 Web 已经是新界面：集成页能显示「本阶段不启用」，新建类型已是「科研项目」。所以未关闭项不能再用「测试环境还是旧包」解释。

## 3. 为什么没解决

### 3.1 方案写了，提交里没有对应改动

I26-06、I26-08、I26-10、I26-12，以及 I26-09 的候选确认面板，都停在文档。`8c5c2a98e` 到 `319a544f3` 改的是导入保护、主 PI 落地、默认流程、Synlora 枚举、基线重建和集成文案。实施状态只记录了这些提交，却按 A–G 的语气让人以为下一轮只剩环境验收。

I26-12 更具体：`ResearchChainSerializer` 已经返回 `owner_name`，总览却仍用课题名轮播。缺的是 `research-home-summary-card.tsx` 和 `research/page.tsx` 的展示，不是再加一个接口。

I26-10 的判断仍然成立：菜单画出来了，值没有提交。`packages/ui/src/dropdown/single-select.tsx` 把选项画成 `fixed`，创建弹层和外层点击检测会在 `onChange` 之前把菜单或弹层关掉。第一轮没有给这条路径补回归，所以「曾修好又出现」仍会复发。

### 3.2 改在重建路径，没有落到正在测试的库

I26-13 的方向节点写在 `build_pi_lab_baseline()`。它只在执行全量重建时创建「基础研究」「产业化」并重挂小组。`prepare_phase15_role_validation` 现在会查找这两个方向，但不会移动已存在的 21 个小组，也不会停用两个验证单元。

当前库正是人工测试库，上面已经有 `QZX-TEST1`、`QZX-TEST2`、周报和绑定。不能为了把树变对而重跑 `rebuild_pi_lab_baseline`。那会按 Excel 重建账号和组织，超出本轮修复。

I26-04 同类：`IntegrationSystem.SYNLORA` 和健康适配器只说明 Plane「能够登记」。`ExternalSystemConnection` 仍是空的，所以页面正确地显示 `not_configured`。2026-09-24 执行手册把「录入 RAGPortal」勾成完成，不能代表 2026-09-27 这个工作区还有这条记录。

### 3.3 修了相邻症状，原症状还在

- I26-02：`platform-settings-form.tsx` 把可见性、应提交范围和上传限制改成了可收缩网格。复核截图里这些区块已经在视口内。剩下的是主 PI 输入框高度小于字形，账号 ID 被底边裁切。继续调列数不会解决。
- I26-03：Web 侧系统管理崩溃已分开。管理端是另一个应用。`apps/admin/app/(all)/(dashboard)/layout.tsx` 在 `isUserLoggedIn === undefined` 时只渲染 `LogoSpinner`。`UserStore.fetchCurrentUser()` 要等 `adminDetails()` 和 `fetchInstanceAdmins()` 都返回才把状态设为真或假。请求挂起时没有超时，所以登录后仍停在标志。原方案里的失败页没有做。
- I26-11：`use-page-fallback.ts` 已改成替换文档，截图正文没有再无限追加。断开后这个 hook 仍会取文档并写回，页面仍在 `Connection lost` 和 `Syncing` 之间切换。连接稳定性和「断开后停止自动改写」是剩余工作。

### 3.4 边界是对的，但现场没有可执行入口

I26-09 不能按库名自动绑定，这个决定保留。复核失败是因为用户连候选都看不到：RAGPortal 未登记，面板仍写「管理员完成该小组的一次手工建库并回填」。测试者无法区分「库不存在」「连接没登记」和「等待确认」。

I26-04 的阶段边界是对的。SpecLabOS、SmartAccess、Poly_Agent、Spec_Agent 继续「本阶段不启用」。需要补的是 dev 上已经在跑的 RAGPortal 和 Synlora，不是把 Phase 2 系统打开。

### 3.5 完成门槛没有卡在人工入口

第一轮要求每项留下自动化、对账和可复现步骤。实际状态文档只记录了前端单测和类型检查，并写明后端 pytest 因开发容器没有 PostgreSQL 没跑。随后没有人用 `100.109.35.2` 把 14 项重新走完。于是「组件测试通过」被当成了「刘俊扬打开总览已经能看到学生名」。

下一轮每项同时满足三件事才算关闭：目标库或目标页面变了、自动化覆盖这次复现、人工按本文第 7 节留下脱敏证据。

## 4. 下一轮原则

- 先修会阻断测试的入口，再迁权限根，再收文案和信息架构。
- 迁移、登记和回填都先 `--dry-run`。失败整批回滚。重复执行不得新建第二套方向节点或第二套连接。
- 不运行 `rebuild_pi_lab_baseline`，不清理 `QZX-TEST1`、`QZX-TEST2` 和已有周报。
- 不把上级写成项目管理员，不把他们加进课题成员 Tab。
- 不因名称相同在生产路径自动绑定「器件」。dev 只有在候选唯一且命令显式确认时才允许回填。
- 密钥只留在现有环境变量和后端密钥库。命令输出、文档和 evidence 只记引用名、状态和 request id。
- 界面改动遵守现有科研页的字号、留白和分隔，不加新的色块或状态徽章墙。只读用一行文字说明。

## 5. 任务卡

### R1 I26-15 上级看到学生项目

**现象。** 科研总览的课题摘要来自研究链 ACL，能看到邱智鑫的两个课题。左侧项目来自 `ProjectViewSet.list`：工作区成员只能看到自己的 `ProjectMember` 或 `network=2`。这两个课题创建时 `network=0`，成员只有所有者和显式协作者。`joinedProjectIds` 又要求 `member_role` 为真，所以侧栏为空。

**读者范围，与课题读权限对齐。**

- 课题所有者的有效直接导师。
- 课题所属组织祖先上、角色为 `PI` 或 `OWNER` 的成员。
- 该工作区配置的唯一主 PI。
- 不包含同组其他学生，不包含仅有工作区成员身份的人。

**实现。**

1. 在 `apps/api/plane/research/views/projects.py` 抽出「研究链只读读者」判断，复用现有导师、祖先组织和主 PI 条件，不另写一套角色。
2. `apps/api/plane/app/views/project/base.py` 的 `list` 和 `retrieve` 把这批私有科研项目并进结果。响应增加 `research_access: "review"`，不改数据库成员行，不伪造 `member_role`。
3. 工作项列表、工作项详情、页面列表和页面详情的项目级读取使用同一判断。写接口、成员管理和项目设置仍要求原有成员角色。
4. `apps/web/core/store/project/project.store.ts` 的 `joinedProjectIds` 纳入 `research_access === "review"`。侧栏项目名旁用现有次级文字标「只读」，不新增彩色标签。
5. 打开项目后，工作项和页面至少可读，包括按编号打开的工作项。项目权限表给这些项目一个访客只读角色，不写入成员行，也不把工作区管理员提升成项目管理员。状态、成员、周期、模块、视图、估算、附件、版本、链接和反应的读取跟着放开，写操作仍拒绝。课题成员 Tab 不出现这些上级。

**测试。**

- 契约：导师能列出并 GET 学生的私有科研项目；无关学生不能；导师 PATCH 项目设置返回 403；所有者行为不变。
- 浏览器：刘俊扬刷新公共工作区后，侧栏和项目页都能看到 `QZX-TEST1`、`QZX-TEST2`；邱智鑫自己的列表不出现导师的其他项目。

**回滚。** 去掉查询条件即恢复原成员列表，没有成员数据要清。

### R2 I26-02 主 PI 输入不被裁切

**现象。** 平台配置的区块已经完整。主 PI 框里的账号 ID 只露出字形上半，底边把字切掉。这不是横向滚动问题。

**实现。**

1. 在 1280 和 1440、浏览器 100% 下检查 `platform-settings-form.tsx` 里主 PI `Input` 的计算高度、行高、内边距和 `overflow`。
2. 让该输入与同页数字输入的可视高度一致，值完整落在框内。长 ID 允许框内横向滚动，不允许被父级裁成半行。
3. 框下增加一行已解析的显示名。解析失败时写「未找到用户」，不把原始 ID 截断当名字。
4. 不改变「只有一位主 PI、只有系统管理员可任命」的规则。

**验收。** 截图中的那串账号 ID 能完整读出，显示名可见。1280 宽没有页面级横向滚动。

### R3 I26-03 管理端离开标志

**现象。** `http://100.109.35.2:3001/god-mode/general/` 在提交密码后一直是居中的 PiLab 标志。登录页本身已经能显示，所以不再把问题收成「端口完全不可达」。

**实现。**

1. 复现时记录登录后挂起的请求：管理端当前用户、实例信息、实例管理员。先确认是超时、401/403，还是根本没有发出。
2. `apps/admin/store/user.store.ts` 的 `fetchCurrentUser` 增加固定超时。超时、网络失败和非 401 的 5xx 都要把 `isUserLoggedIn` 从 `undefined` 改成失败态。
3. `apps/admin/app/(all)/(dashboard)/layout.tsx` 只在请求尚未结束且未超时前显示 `LogoSpinner`。失败时进入已有错误页，写明请求路径和状态码，不写响应正文。
4. 核对管理端 API 基地址和 `CSRF_TRUSTED_ORIGINS` 包含 `http://100.109.35.2:3001`。缺源时补配置并重建对应容器，不改端口猜测算法。
5. 科研 Web 的「系统管理」继续负责导入和邀请码。God Mode 不是组织管理的必经步骤。

**验收。** 正确密码在 8 秒内进入 `/general`，或停在带状态码的失败页。错误密码回到登录错误。两种失败都不再停在标志上。

### R4 I26-04 登记当前 dev 的两个连接

**现象。** 阶段文案已经正确。RAGPortal 和 Synlora 仍是未登记，表单预填 `https://system.example.com`。dev 的两个服务已经在跑。

**实现。**

1. 新增幂等命令 `register_workspace_integrations`。只接受 `public`，系统只允许 `RAGPORTAL` 和 `SYNLORA`。
2. 地址和凭证引用从现有环境读取，不新增第二套密钥：
   - RAGPortal：`http://172.19.0.1:8004`，引用名 `RAGPORTAL_AUTH_SECRET`。
   - Synlora：`http://172.19.0.1:8005`，引用名 `SYNLORA_SERVICE_TOKEN`。
   - 容器网关变化时用命令参数覆盖地址，不把新地址写进仓库。
3. 环境变量缺失时命令失败退出，不写入连接。已有相同系统的连接则更新地址、引用名和启用状态，不新建第二行。
4. 写入后调用现有健康适配器。输出只含系统、状态、耗时和降级原因。
5. 集成表单去掉示例域名占位。未登记时地址框为空，提示「填写该服务从 plane-api 容器可达的基地址」。
6. Phase 2 四项保持「本阶段不启用」，WeKnora 保持「由 RAGPortal 代理」。

**验收。** 刷新系统集成后，RAGPortal 与 Synlora 不再是 `not_configured`。健康失败时显示探针原因，而不是未登记。执行手册 §1 第 6 行改记这次命令的结果，不再沿用 2026-09-24 的勾选。

**回滚。** 命令提供 `--disable`，只把这两行改回未启用，不删除历史健康记录。
