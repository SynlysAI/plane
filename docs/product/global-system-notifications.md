# 全局收件夹与系统通知定义

## 结论

全局收件夹是工作区内的个人通知中心，保留现有 `/:workspaceSlug/notifications/` 入口。项目级 Intake（界面中文为“收集”）不承载系统公告；它继续作为项目请求的进入与审核队列。两者和个人待办的边界如下：

| 模块       | 定位                           | 数据边界                                                    |
| ---------- | ------------------------------ | ----------------------------------------------------------- |
| 全局收件夹 | 每个用户在工作区内收到的事件流 | `Notification` 表按 `receiver` 记录个人已读、归档和暂停状态 |
| 项目收集   | 项目外部或成员提交的待审工作项 | `Intake`、`IntakeIssue` 与 `Issue`，状态由项目审核流程驱动  |
| 个人待办   | 用户需要执行的任务             | 待办任务模型或工作项分派数据，不复用通知模型                |

## 未来系统通知类型

- `version_announcement`：版本公告。发布时面向当时的工作区活跃成员生成个人通知。
- `feedback_result`：用户反馈处理结果。仅发送给反馈提交者和明确指定的项目负责人或处理人。

受众按场景区分：公告采用发布时快照，避免新加入成员被历史公告打扰；反馈结果只做定向投递，不广播给全员。

## 数据依赖与发布模型

后续实现系统通知时，新增一张系统通知内容表，保存标题、正文、通知类型、跳转地址、发布状态、发布时间和创建人。内容表是可审计的通知源，不保存个人状态。

发布成功后，为每一名目标用户写入一条现有 `Notification` 投递记录：

- `entity_name = "system_notification"`
- `entity_identifier = <system_notification_id>`
- `sender = "system:<notification_type>"`
- `data` 保存渲染和跳转所需的最小字段

个人已读、未读、归档和暂停继续复用 `Notification.read_at`、`archived_at`、`snoozed_till`，不另建收件夹状态表。

## 扩展约束

系统通知上线前必须同时完成以下能力，禁止只向 `Notification` 表写入数据：

1. 后端“可展示通知”查询纳入 `system_notification`。
2. 前端通知卡片支持标题、正文摘要、类型标识和跳转渲染。
3. 未读计数与列表、提及/系统分类过滤使用同一口径。
4. 项目收集中的反馈处理完成时，通过发布服务生成 `feedback_result` 通知。

在该能力补齐前，OEVA-003 只将当前可渲染、可打开的工作项通知计入收件夹未读数；研究通知和未来系统通知数据保留在数据库中，但不产生不可见角标。
