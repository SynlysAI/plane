## 1. 背景与生产测试结论

### 1.1 测试背景

2026-10-29 至 2026-10-30，课题负责人在 OpenEVA 生产环境完整测试一条十三阶段科研链。测试覆盖材料上传、材料关联、阶段提交、导师审批、主 PI 审批、任务指派、审批中心、通知和概览展示。

测试结论不是“科研链整体不可用”：单材料阶段可以完成“上传 → 关联 → 提交 → 导师通过”，部分多材料阶段在手动刷新后也能继续。真实问题是闭环可靠性和状态解释不一致，导致用户无法判断下一步，或必须在每个动作后刷新页面。

### 1.2 生产现象归纳

| 编号  | 现象                                                      | 影响                                |
| ----- | --------------------------------------------------------- | ----------------------------------- |
| P0-01 | 每上传或关联一项材料后，需要刷新页面才能继续下一项        | 10 个需要多材料的阶段体验上等于卡死 |
| P0-02 | 需要 PI 的阶段在提交时才暴露英文错误                      | 03/10/11/12/13 对当前课题不可用     |
| P0-03 | 条件升级阶段显示“导师通过，不转 PI”，但请求未显式携带决策 | 07/08/09 卡在待导师审               |
| P1-01 | 课题资料列表长期显示“解析中”，详情接口已是成功            | 用户无法确认引用是否可用            |
| P1-02 | 同一材料行同时出现“满足 / 解析中 / 上传未就绪”            | 状态语义互相冲突                    |
| P1-03 | 历史“补充文字”不计入完成度，但缺少解释                    | 用户误以为已提交材料                |
| P2-01 | 审批完成后课题页计数不自动更新                            | 用户必须手动刷新                    |
| P2-02 | 任务候选为空时没有成员引导                                | 任务无法指派                        |
| P2-03 | 学生看不到自己的阶段审批进度                              | 提交后无法跟踪当前处理人            |
| P2-04 | 通知中英文混排                                            | 中文工作区体验不一致                |
| P2-05 | 概览“最近审批”只看当前阶段                                | 与阶段详情历史不一致                |
| P2-06 | 阶段状态露出 i18n key                                     | 界面不可信                          |

### 1.3 为什么需要 PRD

这些问题不是彼此孤立的 UI 缺陷，而是“上游解析状态、Plane 本地投影、阶段材料完成度、审批状态机、前端局部刷新”五个层次没有形成一致契约。如果只修补按钮，会出现新的状态矛盾。

Phase 1.7 必须先定义产品和状态语义，再由架构设计保证：

1. 同一事实在同一时刻只有一个用户可理解的结论。
2. 所有阻断都有中文原因和解决路径。
3. 材料处理中不阻塞其他材料继续处理。
4. 阶段提交、审批、通知和待办使用同一服务端状态权威。

## 2. 目标、非目标与产品不变量

### 2.1 产品目标

1. **多材料闭环**：所有需要 2 项以上材料的阶段可以连续上传、关联、提交和审批，不需要刷新页面。
2. **主 PI 前置准备**：进入需要 PI 的阶段时即提示配置缺失，并在提交前阻断。
3. **条件升级明确化**：导师对 07/08/09 做出显式“不转 PI / 转 PI”决策。
4. **状态一致性**：材料解析状态、完成度、提交按钮和阶段摘要使用同一规则。
5. **进度可见**：学生能看到自己提交的阶段当前在谁手上。
6. **结果可达**：阶段提交、转 PI、通过、退回产生中文通知。
7. **全局一致**：概览、阶段详情、审批中心不各自维护第二套审批事实。
8. **低疲劳界面**：界面保持学术编辑风格，长时间使用不增加视觉负担。

### 2.2 非目标

- 不新增 `ResearchChain` 主表字段。
- 不把主 PI 冗余复制到课题、链或阶段。
- 不引入新的消息系统或通知表。
- 不重构 Project / ResearchChain / OrgUnit 关系。
- 不改变十三阶段固定顺序和审批状态机。
- 不自动把历史文字材料转换成文件材料。
- 不回写或推翻历史审批结果。
- 不把本阶段扩展为通用工作流引擎。

### 2.3 产品不变量

| 不变量             | 说明                                               |
| ------------------ | -------------------------------------------------- |
| 服务端权威         | 阶段状态、审批资格和材料是否可提交均由服务端判断。 |
| 材料必须可验证     | 只有成功解析的上传记录计入阶段完成度。             |
| 审批不可自审       | 研究负责人不能审批自己的阶段。                     |
| 历史不可篡改       | Chain Event、审计和审核快照继续 append-only。      |
| 权限不因 UI 扩大   | 前端隐藏入口不替代后端 ACL。                       |
| 局部刷新不丢上下文 | 材料操作不得重置节点、知识库和页面滚动位置。       |

## 3. 角色与核心用户旅程

### 3.1 角色

| 角色              | 关键目标                     | 当前痛点                         | Phase 1.7 期望                       |
| ----------------- | ---------------------------- | -------------------------------- | ------------------------------------ |
| 研究负责人 / 学生 | 补齐材料、提交阶段、跟踪进度 | 多材料上传卡住，提交后看不到进度 | 每项材料独立操作，能看到当前处理人   |
| 直接导师          | 审批、退回或决定是否转 PI    | 条件阶段按钮看似可用但后端拒绝   | 明确二选一，结果立即生效             |
| 主 PI             | 处理需要 PI 审核的阶段       | 主 PI 未配置时链路阻断           | 配置缺失提前可见，配置后无需重建课题 |
| 平台 / 组织管理员 | 配置组织、知识库和成员       | 用户不知道入口和责任             | 提示说明配置路径和影响范围           |

### 3.2 旅程 A：多材料提交

```text
选择阶段
  → 查看材料要求
  → 每项要求独立上传并关联
  → 处理中文件自动刷新
  → 全部要求 READY
  → 提交阶段审核
  → 看到当前处理人
```

验收体验：

- 第 1 项上传后，第 2 项上传控件仍可用。
- 文件 A 处理中时，可以继续上传文件 B。
- 材料状态不再同时给出“满足”和“暂不可用”。
- 页面不跳转、不折叠、不丢失当前阶段。

### 3.3 旅程 B：两级审批

```text
学生提交
  → 导师收到通知和待办
  → 导师通过或退回
  → ALWAYS_PI 阶段自动转主 PI
  → 主 PI收到通知和待办
  → 主 PI 通过或退回
  → 学生收到结果通知
  → 课题页阶段计数自动更新
```

验收体验：

- 学生无需切换 admin 账号即可看到阶段在导师或主 PI 手上。
- 审批完成后，已打开的课题页在可见状态下自动更新。
- 通知使用中文并直达阶段面板。

### 3.4 旅程 C：条件升级

条件阶段为 07 实验、08 分析（后）、09 迭代。

```text
学生声明是否需要 PI
  → 提交阶段
  → 导师查看声明
  → 导师显式选择不转 PI 或转 PI
  → 后端按布尔值流转
```

规则：

- 学生声明需要 PI 时，两个选择都可用。
- 学生未声明需要 PI 时，只能不转 PI；转 PI 按钮禁用并说明原因。
- 导师不能通过省略参数让后端猜测。

### 3.5 旅程 D：配置恢复

```text
进入需要 PI 的阶段
  → 阶段卡片提示未配置唯一主 PI
  → 有权限者进入组织设置
  → 配置唯一 primary PI
  → 返回阶段并刷新
  → 提交恢复可用
```

如果当前用户无组织管理权限，提示其联系组织管理员；不显示不可用的高级设置入口。

## 4. 端到端业务流程

### 4.1 材料从上传到计入完成度

| 步骤     | 用户可见                       | 系统行为                       |
| -------- | ------------------------------ | ------------------------------ |
| 选择文件 | 每项材料独立选择               | 前端做类型和大小预检           |
| 上传     | 上传中，按钮保持行内           | BFF 调 RAGPortal，写入本地投影 |
| 关联     | 文件出现在材料行，状态为处理中 | 创建材料条目，但不计入完成度   |
| 解析     | 自动刷新等待时长               | 前端轮询详情，BFF 同步上游状态 |
| 成功     | 已完成，可用于阶段材料         | 计入 `submitted_count`         |
| 失败     | 解析失败和原因                 | 不计入完成度，可重新上传       |
| 全部成功 | 已就绪，可提交                 | 提交按钮启用                   |

### 4.2 阶段提交

1. 服务端确认阶段可编辑。
2. 服务端确认所有材料要求 `READY`。
3. 阶段 03 确认材料预检未过期。
4. 服务端解析唯一直接导师。
5. 按阶段策略确认是否需要唯一主 PI。
6. 写入阶段提交事件、审计、待办和通知。
7. 节点进入等待人工确认。

### 4.3 导师审批

| 阶段策略         | 导师可见操作                            | 服务端结果           |
| ---------------- | --------------------------------------- | -------------------- |
| `ADVISOR_ONLY`   | 通过 / 驳回                             | 通过后阶段和节点完成 |
| `ALWAYS_PI`      | 导师通过，转主 PI / 驳回                | 进入 `AWAITING_PI`   |
| `CONDITIONAL_PI` | 通过（不转主 PI）/ 通过并转主 PI / 驳回 | 按显式布尔值流转     |

### 4.4 主 PI 审批

主 PI 只处理 `AWAITING_PI` 阶段：

- 通过后阶段和节点完成。
- 驳回后阶段和节点回到需修订。
- 结果通知研究负责人。

## 5. 产品规则

### 5.1 上传状态规则

| 状态         | 用户解释 |   是否可关联到材料 | 是否计入完成度 |
| ------------ | -------- | -----------------: | -------------: |
| `PENDING`    | 处理中   | 是，但显示暂不计入 |             否 |
| `PROCESSING` | 处理中   | 是，但显示暂不计入 |             否 |
| `SUCCESS`    | 已完成   |                 是 |             是 |
| `FAILED`     | 解析失败 |                 否 |             否 |
| `DEGRADED`   | 上游降级 |                 否 |             否 |

`PENDING` 是本地投影的初始值，前端与 `PROCESSING` 统一展示为“处理中”。二者不要求用户区分。

需要区分两个动作：

| 动作           | 处理中是否可用 | 说明                      |
| -------------- | -------------: | ------------------------- |
| 关联到阶段材料 |           可用 | 先保留证据，等待解析结果  |
| 确认引用       |         不可用 | 只有 `SUCCESS` 后才能确认 |

处理中点击“确认引用”不能无响应；按钮必须禁用并显示等待原因。

### 5.2 材料要求状态

| 状态         | 触发条件                       | 用户结论             | 提交影响 |
| ------------ | ------------------------------ | -------------------- | -------- |
| `READY`      | 成功数 ≥ 最低数                | 已就绪，可提交       | 不阻塞   |
| `PROCESSING` | 未达标且存在处理中关联文件     | 处理中，暂不可提交   | 阻塞提交 |
| `FAILED`     | 未达标、无处理中且存在失败文件 | 解析失败，需重新上传 | 阻塞提交 |
| `INCOMPLETE` | 未达标且无待观察文件           | 待补充               | 阻塞提交 |

判断优先级固定为 `READY > PROCESSING > FAILED > INCOMPLETE`。即使同时存在失败文件，只要成功数已达标，该材料要求仍为 `READY`；失败文件保留在文件列表中供用户处理。

### 5.3 历史文字材料

- 现有 API 已要求新材料必须提供 `upload_id`。
- 历史文字-only 条目保留展示。
- 展示文案统一为“历史文字记录，不计入完成度”。
- 不自动删除、不自动转换、不伪造上传状态。

### 5.4 已审批阶段与当前材料

已审批阶段的审批结果不可被当前材料投影否定。界面分为两层：

1. **审批结论**：已通过，按审批时快照归档。
2. **当前归档状态**：展示当前材料投影和文件状态。

如果审批快照有效，显示通过时的材料计数；如果历史快照缺失，显示“历史快照缺失，当前材料状态不改变审批结果”。不得把 `已通过 · 0/5` 直接并列输出。

### 5.5 主 PI 配置

主 PI 继续来自组织单元：

1. 优先取唯一有效 primary PI。
2. 无 primary 时，允许唯一有效 PI。
3. 0 个或多个候选均视为未配置唯一主 PI。

阻断规则：

| 阶段策略         | 学生声明  | 未配置主 PI 时 |
| ---------------- | --------- | -------------- |
| `ALWAYS_PI`      | 必须走 PI | 禁止提交       |
| `CONDITIONAL_PI` | 声明转 PI | 禁止提交       |
| `CONDITIONAL_PI` | 不转 PI   | 允许提交       |
| `ADVISOR_ONLY`   | 不适用    | 允许提交       |

项目创建时只提醒，不强制阻断。提醒文案说明后续哪些阶段会受影响，避免用户误解为当前无法创建课题。

### 5.6 条件升级声明

学生在提交 07/08/09 时必须声明是否需要主 PI：

- 声明需要时必须填写升级原因。
- 未声明时仍可走导师单级审批。
- 导师不能替学生修改声明，只能按声明选择是否转 PI。

## 6. 页面与前端信息架构

### 6.1 科研链详情页

保留现有上下文条、Workflow Rail、`overview / nodes / members` 三个 Tab 和 URL 参数，不新增一级导航。

页面职责：

- `overview`：阶段进度、当前动作、最近审批、任务和动态。
- `nodes`：阶段工作台、材料要求、阶段审批、课题资料和科研任务。
- `members`：课题成员管理。

### 6.2 阶段审批要求面板

现有折叠面板保留，内部从上到下为：

1. 阶段摘要行。
2. PI 配置提示。
3. 材料要求列表。
4. 提交审核区。
5. 审批操作区。
6. 历史审核区。

#### 摘要行

显示：

- 阶段审批状态。
- 成功材料数 / 要求组数。
- 当前动作：待补充、处理中、待提交、待导师审、待主 PI、已通过、已退回。

摘要只给一个当前动作，不并列多个结论。

#### PI 配置提示

仅在需要 PI 且配置无效时显示：

- 标题：本阶段需要主 PI 审核。
- 原因：未配置唯一主 PI。
- 路径：组织设置入口或“联系组织管理员”。
- 影响：配置完成前无法提交。

#### 材料要求列表

每个材料要求一行，行内包含：

- 材料名称。
- 成功数 / 最低数。
- 单一状态结论。
- 已关联文件。
- 该行独立的“上传并关联”。
- 该行独立的“关联已有资料”。
- 删除最后一个未提交材料入口。

视觉上使用横向分隔线，不使用彩色卡片。

#### 提交审核区

包含：

- 提交节点选择。
- 条件阶段是否转 PI 声明。
- 升级原因输入。
- 阶段 03 预检状态。
- 提交按钮和缺失原因。

#### 审批操作区

仅当前审核人可见：

- 申请人。
- 当前步骤。
- 最新退回意见。
- 材料变化。
- 意见输入。
- 通过 / 转 PI / 驳回按钮。

### 6.3 课题资料面板

课题资料继续作为节点级资料源，供阶段材料选择。

文件行显示：

- 文件名。
- 大小。
- 状态。
- 等待时长或失败原因。
- 预览 / 下载 / 刷新 / 重新上传。

处理中状态自动刷新，不需要用户手动点击“刷新状态”。手动刷新仍保留作为兜底。

当十三阶段全部通过导致科研链状态可能变为“已完成”时，阶段状态局部刷新必须同步链状态，避免只更新阶段计数而顶部链状态滞后。

知识库未就绪提示只在面板级显示一次：

- 未分配知识库：说明所属团队和管理员处理路径。
- 等待管理员绑定：说明当前不能上传。
- 集成不可用：显示降级原因和重试。

### 6.4 审批中心

现有“科研链阶段 / 阶段评审 / 报告审核 / 办公审批”保留，新增“我的阶段提交”。

#### 我的阶段提交

面向研究负责人：

| 列         | 内容                            |
| ---------- | ------------------------------- |
| 课题       | 课题名称                        |
| 阶段       | 十三阶段中文名                  |
| 状态       | 待导师、待主 PI、已退回、已通过 |
| 当前处理人 | 导师或主 PI；已完成时显示已完成 |
| 更新时间   | 最近提交或审核更新时间          |
| 操作       | 打开阶段审批面板                |

第一版复用 `research-todo.v2` 的 `updated_at` 表示“提交 / 审核更新时间”，不额外扩展响应字段；如果产品后续要求精确区分提交时间，再独立设计 `research-todo.v2.1`。

#### 空态

- 未提交：暂无阶段提交记录。
- 加载失败：无法加载阶段提交，请重试。
- 无权限：当前账号暂无可查看的科研链阶段。

### 6.5 任务创建 Peek

候选人为空时：

- 主文案：本课题暂无可指派成员，请先到成员页添加。
- 操作：前往成员页。
- 保留创建任务标题入口，但指派人可为空或由用户后补，按现有任务规则执行。

搜索无结果时：

- 文案：没有匹配的可指派成员，请调整搜索条件。
- 不显示成员页引导，避免误导。

### 6.6 概览指挥台

“最近审批”改为全链路最新审核记录：

- 审核人。
- 动作。
- 意见第一行。
- 时间。
- 所属阶段。

数据来自当前 `stage-approvals` 响应，不额外请求每个阶段。

## 7. 状态与文案系统

### 7.1 统一文案

| 场景         | 文案                                     |
| ------------ | ---------------------------------------- |
| 上传处理中   | 处理中，预计 30 秒，已等待 {seconds} 秒  |
| 上传成功     | 已完成，可用于阶段材料                   |
| 上传失败     | 解析失败：{reason}                       |
| 上传降级     | 上游暂不可用，暂不能确认解析结果         |
| 材料处理中   | 处理中，暂不可提交                       |
| 材料失败     | 解析失败，需重新上传                     |
| 材料已满足   | 已就绪，可提交                           |
| 材料未满足   | 待补充                                   |
| 历史文字记录 | 历史文字记录，不计入完成度               |
| 主 PI 未配置 | 本阶段需要主 PI 审核，请先配置唯一主 PI  |
| 导师未配置   | 本阶段需要直接导师审核，请先配置唯一导师 |
| 条件未声明   | 学生未声明需要主 PI 审核，不能转主 PI    |
| 任务无候选人 | 本课题暂无可指派成员，请先到成员页添加   |
| 阶段提交成功 | 已提交，等待导师审核                     |
| 阶段转 PI    | 导师已通过，等待主 PI 审核               |
| 阶段退回     | 已退回，请根据意见补充材料               |
| 阶段通过     | 已通过                                   |

“预计 30 秒”是产品默认提示，不是上游承诺。超过 30 秒仍显示真实等待时长并继续刷新，最长自动观察 5 分钟。

### 7.2 错误映射原则

- 不直接展示后端英文 `message`。
- 优先使用 `error_code` 映射中文。
- 审核人配置错误结合 `role` 区分导师和主 PI。
- 材料缺失错误列出中文材料名。
- 未知错误显示“操作未完成，请稍后重试；若持续出现，请反馈给管理员”。

### 7.3 状态标签原则

- 状态文本必须来自映射表或 i18n key。
- 未知状态显示“状态未知”。
- 禁止把 `research.chains.node_status.in_progress` 这类 key 暴露给用户。
- 状态不单靠颜色区分，必须包含文本。

## 8. 错误恢复与空态设计

### 8.1 上传失败恢复

1. 保留失败记录和失败原因。
2. 提供重新上传入口。
3. 用户重新选择文件后走原上传校验和幂等逻辑。
4. 不假装能从 Plane 重新触发上游解析，因为文件内容保存在外部系统。

### 8.2 解析超时

- 自动轮询最长 5 分钟。
- 超时后显示“仍在处理中，可稍后返回查看”。
- 保留手动刷新。
- 不把超时自动改成失败，除非上游明确返回失败。

### 8.3 关联失败

- 显示具体错误。
- 已成功上传的文件保留在课题资料列表。
- 用户可重试关联，不需要重新上传。

### 8.4 局部刷新失败

- 保留已有页面数据。
- 显示“阶段状态刷新失败，请重试”。
- 不清空材料列表、不折叠面板、不重置滚动位置。

## 9. 无障碍与响应式要求

### 9.1 无障碍

- 处理中区域：`role="status"`、`aria-live="polite"`。
- 错误：`role="alert"`。
- 禁用按钮：提供可见原因或 `aria-describedby`。
- 每个材料上传 input 的 `aria-label` 包含材料名称。
- 条件审批按钮文本明确区分“不转主 PI”和“转主 PI”。
- 键盘可完成阶段展开、文件选择、材料关联、提交、审批和历史查看。
- 局部刷新不得导致焦点丢失或跳回页面顶部。

### 9.2 响应式

| 宽度  | 要求                                       |
| ----- | ------------------------------------------ |
| ≥1440 | 阶段材料与提交审核保持双栏。               |
| 1280  | 双栏不横向溢出，长文件名截断并提供 title。 |
| 390   | 材料行、操作按钮和审批按钮纵向堆叠。       |

## 10. 验收场景与发布指标

### 10.1 必须通过的场景

1. 02 选题 5 项材料连续上传并提交。
2. 05 分析（前）3 项材料连续上传并提交。
3. 06 开题 7 项材料连续上传并提交。
4. 12 结题 2 项材料连续上传并提交。
5. 07/08/09 条件阶段分别验证不转 PI 和转 PI。
6. 03/10/11/12/13 在主 PI 未配置时被前置阻断。
7. 配置唯一主 PI 后，无需重建课题即可提交。
8. 学生在审批中心看到阶段当前处理人。
9. 导师或主 PI 审批后，学生打开的课题页自动更新计数。
10. 阶段通过或退回后学生收到中文通知。
11. 概览最近审批与阶段详情历史一致。
12. 新建节点后不再出现 i18n key。

### 10.2 发布指标

- 多材料阶段完成一次材料关联不需要整页刷新。
- `PROCESSING` 材料不再被计入可提交完成度。
- 审批相关用户错误文案中不出现英文规则句。
- 阶段审批列表查询数不超过既有契约上限。
- 我的阶段提交不在前端按课题循环请求。
- 1440 / 1280 / 390 宽度无横向溢出。

## 11. 代码事实附录

| 领域         | 当前事实                                                                             | 产品含义                     |
| ------------ | ------------------------------------------------------------------------------------ | ---------------------------- |
| 上传模型     | `ResearchChainUpload.Status` 包含 `PENDING/PROCESSING/SUCCESS/FAILED/DEGRADED`       | 需要统一展示和完成度语义     |
| 上传列表     | `GET /uploads/?node_id=` 只读本地投影                                                | 不能期待列表自动刷新上游     |
| 上传详情     | `GET /uploads/{id}/` 调 RAGPortal 并回写本地状态                                     | 适合作为前端轮询入口         |
| 材料投影     | `LINKABLE_UPLOAD_STATUSES = {PROCESSING, SUCCESS}`，当前两者均计入 `submitted_count` | 需要拆分“可关联”和“可计入”   |
| 阶段面板     | 一个 `requirementCode` 和一个上传控件服务全部材料                                    | 是多材料操作卡住的直接来源   |
| 课题详情刷新 | 材料关联后调用整页 `load()`                                                          | 容易重置节点和知识库控制器   |
| 知识库控制器 | 绑定全局注意力节点，不是阶段首选节点                                                 | 阶段面板可能读错资料范围     |
| PI 解析      | 从组织单元成员解析，未配置时抛规则错误                                               | 应提前提示并映射中文         |
| 条件审批     | 后端要求显式 `escalate_to_pi`                                                        | 前端 false 不能省略          |
| 我的阶段     | `research-todo` 只投影待审阶段，`mine` 用 `chain.owner`                              | 需扩展 owner 视角结果        |
| 通知         | 阶段审批尚无通知 helper                                                              | 复用既有 Notification 表补齐 |
| 工作项通知   | 前端通知内容 map 硬编码英文                                                          | 展示层 i18n 即可修复历史数据 |
| 概览         | “最近审批”只取当前阶段最后一条                                                       | 应从全部阶段聚合             |
