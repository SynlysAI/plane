## 1. 背景与问题

Phase 1.5 已经交付科研项目、报告、成果、反馈和角色筛选的主要浏览与协作能力，但产品语义仍存在三类收敛需求：

1. **课题与项目混淆**：用户需要在 Research Chain 与 Project 之间判断科研过程和行政事务的归属，容易出现同一事项重复建链、重复建项目或审批链割裂。
2. **界面信息偏多**：部分页面仍同时承担浏览、管理、统计和过程操作，用户需要理解过多入口和筛选条件才能找到下一步动作。
3. **实现存在历史残留**：Phase 1.5 的多轮修正留下了重复展示分支、兼容状态和未被引用的逻辑，继续累积会增加后续 Phase 2 的维护成本。

Phase 1.6 不通过推翻基础设计解决上述问题，而是在保持现有技术事实的前提下收敛产品语义、角色视图和代码治理规则。

## 2. 目标、非目标与不变量

### 2.1 产品目标

- 厘清课题链与 Project 的职责边界，让科研主线和行政事务有稳定、可解释的归属规则。
- 通过“首页两列工作台、科研 / 行政项目分流、一级导航去重”精炼科研空间的信息层级和角色看板。
- 建立代码精炼原则，为后续实施提供可审计的引用清单、兼容清单和回归清单。
- 通过预开题、周报、论文修改评审三个业务样例验证课题链语义，但不把它们单独作为阶段节点。

### 2.2 非目标

- 不修改业务代码、数据库结构、API 契约、路由行为、权限实现或部署配置。
- 不迁移历史课题、Project、报告、审批、事件或附件数据。
- 本阶段不直接修改 Markdown 编辑器代码或新建独立编辑器产品；但必须冻结“可靠粘贴、结构化 Markdown 导入、图片上传、保存状态、版本只读”的实现合同，并在后续实现切片中验收。
- 不在本轮修改真实路由、模型或权限实现；目标 IA 仅作为 Phase 1.6 产品设计与静态原型口径。
- 不接入新的专业系统，不改变 Phase 2 的垂类能力边界。
- 不执行实际代码删除；本阶段仅输出清理原则与候选范围。
- 不在本阶段实现偏差检测模型；本阶段冻结偏差检测的触发、证据、人工确认和通知合同，避免把未来 AI 结论当作科研事实。

### 2.3 基础设计不变量

以下设计是 Phase 1.6 的前置约束，任何后续实施方案都不得默认改变：

- 保留现有 Research Chain 节点类型、主链结构、循环节点、状态机、快照、事件、反思和 Trace 模型。
- 保留现有组织树、组织成员、课题组主 PI、直接导师、组织向上继承和对象 ACL 判定规则。
- 保留现有 Project、Issue、Page、Approval Request、FileAsset 等权威对象及其权限链路。
- 保留现有 Workspace capability、科研模块开关、`research_ia_v2` 回退能力和旧路由兼容策略。
- 不拆除 Research Chain 与 Project 的现有技术关系，不新增平行课题系统。
- 不改变主 PI / 导师角色解析、审批范围、默认拒绝和组织继承优先级。

## 3. 主轴一：课题与项目管理的逻辑厘清

### 3.1 通道语义

| 维度     | 课题链 / Research Chain                   | Project                                    |
| -------- | ----------------------------------------- | ------------------------------------------ |
| 产品职责 | 科研主线和科研过程治理                    | 行政事务与通用项目协作                     |
| 典型对象 | 课题、节点、快照、事件、报告、评审、Trace | 行政任务、采购、报销、设备协作、通用 Issue |
| 时间模型 | 科研阶段与节点流程                        | 项目周期、行政截止时间和协作安排           |
| 权限模型 | 课题 ACL、组织继承、科研角色和对象 ACL    | Project 成员、Issue 权限和审批配置         |
| 结果沉淀 | 科研事实、过程回放、评审结论和正式产物    | 行政回执、协作记录和事务状态               |

课题链面向科研主线，承载开题、文献调研、实验记录、中期检查、论文写作、评审结论和过程沉淀。Project 面向行政事务与通用协作，承载采购、报销、行政审批、设备协作和非科研事项。两者是职责边界不同的工作通道，而不是互相替代或合并的两套系统。

### 3.2 任务归属规则

- 科研任务必须挂到课题节点或课题关联的科研流程对象上，可指派责任人、设定截止时间、提交产物并进入 Review。
- 行政任务留在 Project / Issue / Approval 通道，不进入课题链流程。
- 同一事项在创建时应先判断属于科研主线还是行政事务，避免同时生成课题节点和行政 Issue。
- 既有混合项目不做历史数据搬迁；Phase 1.6 仅通过入口、文案和列表上下文区分两类事项。
- 系统不自动把 Project 任务转换成课题节点，也不自动把科研节点投影为行政 Issue。

### 3.3 权限与可指派范围

Phase 1.6 沿用现有四层权限判断：Workspace 能力、科研角色、课题访问、对象动作。上层权限不得静默扩大下层对象可见性。

- **科研节点任务**：可指派候选人由当前课题所属组织及其祖先组织的有效成员，加上已显式加入该课题的跨组织协作者组成；下级组织成员、Guest、失效成员和仅有 Workspace Admin 身份的用户不自动出现。候选人必须通过服务端 `assignable-users` 返回，前端只能在已返回集合内搜索。
- **行政项目 / Issue**：可指派候选人只能来自该行政 Project 的有效 `ProjectMember`；若项目启用审批流，审批人仍由 `ApprovalRequest` 的流程步骤解析，不能用 Issue 负责人下拉替代审批人。行政项目的负责人下拉与科研节点任务下拉是两套来源，不能混用。
- 科研任务指派时下拉按“组织范围 / 显式协作者”分组，并展示组织、科研身份和可执行范围；行政任务下拉按“项目成员”分组，并展示项目角色。
- 直接导师、课题组主 PI、必评人和明确指派人按现有审批范围获得对应动作权限。
- 跨组织协作者必须显式加入课题，并通过课题 ACL 与对象 ACL 校验。
- Workspace Admin 可以管理组织、成员、配置和审计，但不因管理员身份自动获得科研评审权。
- 无权限对象在列表、计数、详情和导出中保持不可见；权限不足文案不得泄露对象标题或正文。
- 选择候选人不等于把用户加入课题或行政项目；新增成员必须走既有成员管理流程。候选人接口返回空集合时，表单必须阻止提交并给出“当前范围无可指派用户”的恢复路径。

### 3.4 业务样例定位

预开题、周报、论文修改评审用于验证课题链语义，不是独立阶段节点。

- **预开题**：学生提交材料后进入课题节点，Synlora Agent 提供形式审查与先进性初判参考，直接导师在线评议并迭代，最终由配置化最终确认人确认。AI 结果仅辅助，不替代人工决策。
- **周报**：周期报告属于科研过程事实，提交后进入导师待办。导师打开详情即形成服务端已读回执；已读与接受、退回等审阅结论分离。
- **论文修改评审**：论文版本、修改说明、导师评论、作者迭代和最终确认均关联课题节点，保留完整沟通与版本轨迹。
- **Agent 契约**：Plane 只对接 Synlora Agent；Deepseek 等具体模型只能作为 Synlora 的底层配置，不进入 Plane 产品契约。
- **Trace 契约**：评论、人工决策、AI 交互摘要和状态变化继续沉淀在现有 Chain Event / Trace 体系中，不复制聊天正文或外部系统原始数据。

## 4. 主轴二：UX 精炼

### 4.1 信息架构原则

Phase 1.6 将现有产品语义收敛为五个一级导航入口，但不改变科研链 Workflow Rail、节点详情、审批中心和科研管理的业务骨架：

- 首页直接承载项目概览、跨组件待办、最近动态和提交汇总。
- 左侧导航仅保留一列 250px Projects 侧栏；顶部导航保留，App rail 不再出现在目标原型中。
- 一级导航固定为：首页、管理、审批中心、科研项目、行政项目。
- “管理”是原“科研管理”的目标展示名，底层仍映射 `/{workspace}/research/settings` 与既有科研管理能力。
- 科研项目与行政项目父级本身可点击，分别进入对应工作台；其具体项目作为二级导航项显示。
- 科研项目父级进入“科研项目 / 报告”工作台，行政项目父级进入“项目 / 视图 / 分析 / 归档”工作台。
- 二级科研项目进入科研项目详情；二级行政项目复用行政项目页“项目”Tab，本轮不新增行政详情页。
- 科研项目页面只展示 Research Chain 课题链和报告，不展示行政 Project。
- 行政项目页面承载普通 Plane Project 的项目、视图、分析和归档能力，不与科研链混合。
- 审批中心按待处理类型聚合，减少重复入口、重复筛选和重复统计。
- 科研项目与行政项目通过导航、文案、路径上下文和空态明确区分。
- 页面主操作通常只保留一个；浏览、筛选和管理操作不得竞争同一视觉层级。

首页采用固定两列布局：

| 列       | 内容                                   | 规则                                         |
| -------- | -------------------------------------- | -------------------------------------------- |
| 项目概览 | 上方为科研项目概览，下方为行政项目概览 | 两类项目不得混合成同一个列表或同一组卡片     |
| 待办动态 | 跨组件待办、最近动态、报告提交汇总     | 按截止时间与紧急程度排序，每条待办直达上下文 |

首页不再显示快捷入口、我的工作、草稿、便签等通用首页模块；这些能力保留在原有路由和产品入口中，不迁移、不删除数据。

Phase 1.6 目标语义合同：

| 名称     | 产品含义                                               | 数据口径                                                                     |
| -------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 科研项目 | 科研主线、13 段 Workflow、节点任务、报告、评审与 Trace | 展示 Research Chain；关联科研 Project 仍是内部权威关系，不在行政列表重复展示 |
| 行政项目 | 采购、报销、设备协作、办公审批、普通 Plane 协作        | 展示不带科研主线语义的普通 Plane Project / Issue / Approval                  |
| 报告     | 周报、阶段报告及其审核 / 已读状态                      | 归属科研通道，在“科研项目”页作为二级 Tab                                     |
| 办公审批 | 行政事务审批                                           | 归属行政通道，在审批中心保留 `office` Tab                                    |

未来实现时的路由兼容口径：

- `/{workspace}/` 承载首页与科研总览。
- `/{workspace}/research/chains` 显示“科研项目”，内部 Tab 为“科研项目 / 报告”。
- `/{workspace}/projects` 显示“行政项目”，内部 Tab 为“项目 / 视图 / 分析 / 归档”。
- `/{workspace}/research/approvals` 与 `/{workspace}/research/settings` 保留。
- `/{workspace}/research/settings` 的目标页面标题显示为“管理”，不改路由和权限。
- 旧 `/{workspace}/research` 科研总览入口应兼容重定向到首页，不允许直接破裂。
- 本阶段仅输出设计与原型，不修改真实路由。

### 4.2 角色化看板

| 角色            | 核心看板                                         | 主要下一步                         |
| --------------- | ------------------------------------------------ | ---------------------------------- |
| 学生            | 我的科研项目、节点任务、待提交材料、待修改意见   | 提交、修改、确认评审意见           |
| 直接导师        | 待阅读周报、待评审材料、待指导项目、学生进展摘要 | 阅读、评论、退回、通过             |
| 课题组主 PI     | 课题组任务分布、阻塞事项、评审进度、成员负载     | 分派、协调、处理阻塞、复核         |
| Workspace Admin | 组织、成员、配置、审计、行政项目                 | 维护配置与组织，不默认介入科研评审 |

角色看板是现有数据的视图重组，不新增权限事实源。角色缺失、数据不可访问或功能关闭时显示中性状态，不显示伪造计数。

### 4.3 体验细节要求

- To-Do List 显示责任对象、责任角色、截止时间、倒计时和下一步动作；逾期或临近截止使用克制的红色警示。
- 流程到达责任人时发送明确通知，通知可直达课题节点、报告详情或审批上下文。
- Markdown 编辑能力以保留结构、可靠粘贴、清晰保存状态为目标；不改变现有编辑器权威对象和版本链路。
- loading、empty、forbidden、degraded、saving、error 等状态使用中文说明，提供恢复或替代路径，不暴露原始错误码。
- 所有新增或调整文案必须能区分“科研过程”和“行政协作”，避免继续使用含混的“项目”一词指代课题。

### 4.4 Tower 式统一指派与待办体验

初始目标中的“科研节点任务、周报提交、论文评审需要他人处理”统一进入一个待办入口，交互参考 Tower 的任务处理方式：用户首先看到“我需要处理什么”，打开后看到业务上下文、发起人、当前负责人、当前状态和下一步动作；业务对象仍各自保存正文、版本、评论和领域状态。

#### 4.4.1 统一待办信封

Phase 1.6 不新增一个覆盖任务、报告、论文和审批的通用业务表。服务端新增只读的 `research-todo.v2` 投影（可由现有对象查询聚合），每条待办至少包含：

| 字段              | 含义                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------- |
| `id`              | `source:object_id[:assignment_id]`，用于去重和幂等展示                                      |
| `source`          | `CHAIN_TASK`、`REPORT`、`PAPER_REVIEW`、`STAGE_REVIEW`、`AGENT_APPROVAL`、`OFFICE_APPROVAL` |
| `object_id`       | 业务对象 ID；不复制正文                                                                     |
| `title/context`   | 可见范围内的标题、课题、节点和周期摘要                                                      |
| `requester`       | 提交或发起人                                                                                |
| `assignees`       | 当前负责人/处理人；可能是一人或审批流解析出的多人                                           |
| `business_status` | 原对象状态，如 `SUBMITTED`、`NEEDS_REVISION`、`WAITING_REVIEW`                              |
| `handling_status` | 统一展示态：`TODO`、`IN_PROGRESS`、`RETURNED`、`DONE`、`BLOCKED`                            |
| `next_action`     | 当前用户可执行的动作，如 `READ`、`REVIEW`、`SUBMIT`、`RETURN`、`ACCEPT`                     |
| `due_at`          | 截止时间，没有截止时间时为空                                                                |
| `href`            | 深链到业务对象上下文                                                                        |
| `capabilities`    | 服务端计算的动作集合，不由前端角色名称推断                                                  |
| `trace_ref`       | 业务对象的审计/Trace 引用                                                                   |

`requester`、`assignees`、`business_status` 和 `handling_status` 必须同时展示，避免把“谁提交”和“谁处理”混为一个“负责人”字段。没有当前处理人的待办只允许在“我发起”或“全部可见”中出现，不进入“我可处理”。

#### 4.4.2 各业务对象的映射与闭环

| 业务对象     | 指派来源                                                               | 待办触发                                  | 处理动作                    | 退回/重提闭环                                                         |
| ------------ | ---------------------------------------------------------------------- | ----------------------------------------- | --------------------------- | --------------------------------------------------------------------- |
| 科研节点任务 | 显式 `assignee`，候选人遵循当前组织+祖先组织+显式协作者范围            | `ASSIGNED`、`SUBMITTED`、`NEEDS_REVISION` | 责任人提交；评审人退回/完成 | `SUBMITTED → NEEDS_REVISION → SUBMITTED → COMPLETED`                  |
| 周报         | 提交时由现有 direct advisor / 管理范围解析当前处理人；不把作者当处理人 | `SUBMITTED` 且当前用户可阅读/审阅         | 阅读、接受、退回            | `SUBMITTED → NEEDS_REVISION → SUBMITTED → ACCEPTED`；已读回执独立记录 |
| 论文评审     | `final_reviewer` 和既有课题 ACL；作者负责重新提交版本                  | `WAITING_REVIEW`、`NEEDS_REVISION`        | 评审人评论、接受、退回      | `WAITING_REVIEW → NEEDS_REVISION → WAITING_REVIEW → ACCEPTED`         |
| 阶段评审     | 现有 `StageReviewerAssignment`                                         | 阶段提交后按 assignment 生成              | 评审、修订、催办            | 保留现有 StageReview/Revision 状态和规则                              |
| Agent 审批   | 现有 Agent approval 的请求人/当前审批人                                | Agent 请求等待人工确认                    | 批准、拒绝、查看材料        | 保留 Agent 审批状态，不转写科研任务状态                               |
| 办公审批     | `ApprovalRequest` 当前 flow step 的 approver                           | 当前步骤待审批                            | 批准、驳回、撤回            | 保留 ApprovalAction 和 Issue 状态推进                                 |

统一入口只统一“查看与动作编排”，不统一这些业务状态。每个动作必须回到原对象 API，服务端使用现有 `check_access`、`can_act_on_current_step`、reviewer assignment、ProjectMember 和对象 owner 规则判权。

#### 4.4.3 统一范围、排序与状态

- `我可处理`：只返回当前用户存在可执行 capability 且业务状态允许动作的待办。
- `我发起`：返回当前用户提交/创建的事项及其当前处理人、处理状态和退回原因。
- `全部可见`：先执行业务对象 ACL，再返回当前用户可查看的待办，不扩大正文可见范围。
- 默认排序：`BLOCKED/逾期` → 今天截止 → 其他截止时间 → 最近更新时间；同一 `id` 只保留一条。
- “已读”不是“已审阅”，“已打开”不代表“已完成”；周报已读回执和业务审阅结论继续分离。
- 动作按钮按服务端 `capabilities` 渲染；执行期间显示保存中，冲突时保留页面上下文并提供刷新。

#### 4.4.4 审计和通知

统一投影本身是只读的，不写审计。指派、提交、打开正式周报、评论、退回、接受、重新提交分别由原业务服务写入既有 Chain Event、ReportReviewLog、StageReviewRevision、ApprovalAction 或审计事件；通知继续使用现有 Notification 管线，数据中带 `source/object_id/assignment_id/href`，确保从通知直接回到待办上下文。

#### 4.4.5 当前实现差距

当前代码已有前端 `collectResearchTodos`，但它是跨服务的前端聚合，尚未包含节点任务和论文评审，也没有统一的 `requester/assignees/handling_status/capabilities` 信封；报告处理人由 ACL 推导，阶段评审已有 assignment，办公审批已有当前步骤。后续实现应先提供服务端 `research-todos` 只读聚合，再逐步替换前端扇出，避免先做一套新的前端状态机。

#### 4.4.6 实施顺序与范围控制

按以下顺序实施，每一步都能独立回滚：

1. **契约与投影**：冻结 `research-todo.v2` 字段、六类来源的状态映射、三种 scope、稳定 `todo.id` 和 capability 语义；先用现有任务/报告/阶段评审/审批数据生成只读接口。
2. **统一入口**：首页与审批中心改为消费同一投影，保留领域队列和旧深链；前端保留现有 `collectResearchTodos` 作为降级路径，服务端接口稳定后再收敛扇出请求。
3. **领域补齐**：接入节点任务和论文评审的待办来源，补齐周报已读待办；不改既有业务对象的状态机和写 API。
4. **动作回流**：统一入口只导航并调用领域动作，成功后刷新投影；补充并发冲突、权限拒绝、部分来源降级和通知深链验收。
5. **清理重复**：只有在服务端投影、领域动作和回归证据稳定后，才删除前端重复聚合或重复入口；删除前完成引用、兼容和回滚审计。

本阶段不做统一业务任务表、不做跨对象状态迁移、不把审批人改造成普通负责人，也不把待办列表扩展成第二套编辑器或评论系统。

## 5. 主轴三：代码精炼

### 5.1 清理原则

- 优先删除确认不可达、无兼容责任、无数据影响且未来大概率不复用的 UI、状态、工具函数和测试夹具。
- 保留仍承担兼容、审计、权限、迁移或外部契约责任的代码。
- 不为减少代码量牺牲节点结构、组织继承、ACL、API、数据和路由兼容性。
- 删除前必须证明引用为零，或明确保留入口、数据迁移和兼容期。
- 清理过程小步提交，每一步可独立回滚。

### 5.2 候选范围

- Phase 1.5 后遗留的重复列表组件、兼容展示分支、无效筛选状态和未使用文案。
- 只服务于旧交互且已被课题链容器替代的展示逻辑。
- 重复的数据组装逻辑和未被引用的服务方法。
- 仅用于历史验证、当前测试不再依赖且不承担回归语义的夹具。

### 5.3 实施门槛

实际代码精炼必须另行建立实施清单，并满足以下门槛：

1. **引用清单**：列出被删符号、路由、事件、文案和测试的所有引用来源。
2. **兼容清单**：确认不涉及公开 API、数据库字段、外部回调、审计事实、权限能力和旧路由兼容期。
3. **回归清单**：至少覆盖科研导航、课题链、报告、审批、权限和普通 Plane 项目能力。
4. **评审记录**：删除理由、保留理由、回滚方式和验证结果必须写入对应实施计划。
5. **迁移边界**：涉及数据库或公开 API 的废弃不直接执行，必须单独设计兼容期与迁移策略。

## 6. HTML 原型要求

Phase 1.6 交付一个自包含静态原型：[`phase-1.6-research-space.html`](prototypes/phase-1.6-research-space.html)。

原型是**产品界面型原型**，不是功能介绍页：

- 直接用浏览器打开，不依赖后端、构建工具或外部网络。
- 复刻目标应用外框：顶部导航、一列 250px Projects 侧栏和带边框的主内容区；不渲染 App rail。
- 使用 Phase 1.6 目标 IA：首页、管理、审批中心、科研项目、行政项目五个一级入口。
- 覆盖七个真实页面：
  1. 首页（项目概览列 + 待办动态列）
  2. 科研项目（科研项目 / 报告两个视图）
  3. 行政项目（项目 / 视图 / 分析 / 归档四个视图）
  4. 科研项目详情（13 段 Workflow 和四个 Tab）
  5. 周报详情（已读与审阅分离）
  6. 审批中心（阶段评审 / 报告审核 / Agent 审批 / 办公审批）
  7. 管理（原科研管理）
- 支持四类原型角色切换：学生、直接导师、课题组主 PI、Workspace Admin。
- 角色切换只影响示例数据，不模拟权限系统，也不出现在生产产品需求中。
- 页面主体不得再用概念卡片解释三大主轴；设计说明保留在文档中。
- 原型必须标注“静态原型，非功能实现”，不伪造真实系统状态、审批结论或 AI 结果。
- 原型必须演示两套指派下拉：科研节点任务使用“组织范围 / 显式协作者”候选；行政项目使用“当前 Project 成员”候选。切换角色时，示例候选与可操作提示同步变化；提交仅模拟界面反馈，不写入真实系统。
- 原型必须演示 Tower 式统一待办入口：范围切换、业务来源、发起人、负责人、业务状态、处理状态、下一步动作、截止时间和深链；节点任务、周报、论文评审、阶段评审和办公审批在同一列表中可区分但不混淆。

视觉要求：

- 使用当前 Plane / Propel light token 与现有科研页面组件密度。
- 保持 Academic Editorial UI 的克制原则：排版驱动层级、单一强调色、克制边框和背景。
- 禁止渐变、发光、彩色卡片、装饰图形和 AI 风格徽章。
- 紧急状态只使用克制红色，并同时携带“逾期 / 今天截止”文字。

## 7. 验收口径

Phase 1.6 的文档与原型验收以三大主轴为准：

1. **逻辑厘清**：课题链与 Project 的职责、任务归属、权限口径和业务样例归属可被产品、开发、测试共同复述。
2. **UX 精炼**：产品级原型能展示顶部导航 + 单列侧栏、首页两列布局、五入口项目树、科研项目 / 行政项目分流、课题详情四 Tab、审批中心四队列和四类角色工作台；左侧导航中“首页”只出现一次且只有一个可点击入口。
3. **代码精炼**：清理原则、候选范围、实施门槛和回归范围已冻结，后续实施不需要重新决策边界。
4. **不变量验证**：文档明确节点结构、组织继承、ACL、权威对象和既有 API 均不变。
5. **原型质量**：桌面与窄屏布局可用、交互无控制台错误、灰度层级清晰、视觉克制并适合长时间阅读。
6. **目标覆盖**：初始目标矩阵中的每一项都能在 PRD、三份开发设计和原型中找到唯一对应的对象、页面、接口或明确的后续阶段边界。
7. **指派边界**：科研候选人集合与行政候选人集合来源不同；任一表单不得出现全工作区自由搜索或越权候选人。
8. **统一待办**：同一事项在首页和待办中心使用同一 `todo.id`、状态映射、负责人和动作能力；点击动作后回到对应业务对象，不由待办中心复制业务状态机。
