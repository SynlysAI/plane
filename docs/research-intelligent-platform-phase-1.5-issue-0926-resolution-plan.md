## 1. 结论

0926 不是一批互不相干的页面问题。它们来自六组已经存在、但没有在界面上说清楚的双轨：

1. **工作区双轨。** 业务数据只在 `public`。`pi` 是主 PI 壳，聚合接口对 `PI_PRIVATE` 故意返回不存在。登录却跟随 `last_workspace_id`，所以洪文晶会进主 PI 工作区，总览再把这件预期内的事画成红色「汇总加载失败」。
2. **组织双轨。** 权限继承靠组织 `path`。业务方向目前只是小组上的 `business_category` 标签。Phase 1.5 又造了两个没有父节点、层级为 0 的「验证单元」。标签、悬空节点和真实小组因此是三套结构。
3. **知识库双轨。** RAGPortal 自己能列出「器件」等库。Plane 的小组绑定仍是 `PENDING_ADMIN`，集成登记也是 `not_configured`。库在别的系统里可见，不等于 Plane 已经绑定。
4. **资料双轨。** 课题 Tab、节点按钮、成果登记、周期报告正文、确认快照是五种对象，界面用了同一组词。
5. **流程双轨。** 新建项目默认仍是「培养项目（旧流程）」。平行科研课题才是现行模式，项目类型只应保留为属性标签。
6. **阶段双轨。** SpecLabOS、SmartAccess、Poly_Agent、Spec_Agent 属于 Phase 2。把「本阶段不启用」显示成「未配置故障」，会让测试误判联调失败。

本轮要先止住会改写数据或阻断测试的缺陷，再改组织这个权限根，最后收信息架构。不要为了让截图变绿去自动绑定生产知识库，也不要在本阶段实现湿实验调度。

建议顺序：周报正文回退循环、系统管理整页崩溃、工作项下拉、主 PI 落地与假失败、组织层级、总览人名与行数、知识库确认绑定、研究链信息架构、集成页说明、平台配置密度。

## 2. 判读原则

- 权限问题先看组织 `path` 和动作，不看页面上的业务分类下拉。
- 同一个中文词先对到对象，再决定是缺陷还是缺说明。至少分开：周期报告、成果著录、课题资料、节点材料、确认快照、外部资产。
- RAGPortal 页面健康，不能证明 Plane `ExternalSystemConnection` 已登记。
- `not_configured` 在本阶段只对 RAGPortal 构成缺口。其余四个生态连接保持停用，并改文案。
- 人工测试知识库仍只允许确认 `plane测试`。同名「器件」库只能提示，不能自动变成 `READY`。
- 学生、导师、方向负责人和主 PI 的可见范围不在本轮放宽。总览只改变已经可见条目的人名和排数。
- 旧流程数据保留可追溯记录，新建入口不再提供。

## 4. 分项分析与方案

### 4.1 I26-01 系统管理整页崩溃

组织架构下的「系统管理」是科研设置页，不是 God Mode。它同时放管理员标签、邀请码和用户导入。现场落到 Web 错误页 “Looks like something went wrong”，这是 `apps/web/app/error/prod.tsx` 的整页边界。

导入面板对请求失败有自己的提示，不会主动把整页打到错误边界。因此崩溃发生在渲染，而不是导入接口返回了业务错误。这个页面独有的新数据，是基线重建写下的 `IMPORTED` 批次：约 189 行，来源文件名拼接了两张 Excel，行上还可能带初始密码。打开该批次后，`ImportReview` 会一次渲染全部行。

方案：

- 用当前这个真实批次复现，保留浏览器调用栈。不要先重新导入，否则会覆盖现场。
- 路由内再套一层局部错误边界。导入表格出错时，组织树和邀请码仍可使用。
- 列表接口只回摘要。详情分页，每页不超过 50 行。任何导入响应都不含 `initial_password`；密码只走已有的一次性报告下载。
- 未知 `admin_roles` 显示原值，不把缺失文案传进翻译函数。
- 历史批次的「下载导入报告」保持显式动作，系统管理页加载时不自动展开 189 行。

验收：管理员打开系统管理、打开基线批次、翻页和下载报告都不进入整页错误边界。响应体抽查没有密码字段。

### 4.2 I26-02 平台配置显示不全

平台配置本身已有 `md:grid-cols-3` 和 `md:grid-cols-4`。在科研侧栏加上 100% 缩放时，主 PI 说明「仅系统管理员可任命唯一主 PI，请填写账号 ID 或邮箱。」和四个限制字段仍会挤出视口。用户要的是把密度降下来，而不是再放一个横向滚动条。

方案：

- 宽度低于 1280 时，可见性、应提交范围和上传限制都改为单列。
- 说明文字允许换行，控件 `min-w-0`，页面只保留纵向滚动。
- 主 PI 输入框单独占满一行，保存结果留在表单顶部。
- 1440×900 和 1280×800、浏览器 100% 时，不出现横向滚动，主 PI 说明完整可见。

这是展示修复，不改主 PI 只能有一位、只能由系统管理员任命的规则。

### 4.3 I26-03 PiLab Admin 停在标志

God Mode 和管理端启动页在实例信息返回前只渲染标志。`resolveGodModeUrl` 会把配置里的主机改成当前访问主机；配置没写端口时，还会沿用当前页面端口。测试入口是 Tailscale 上的 Web `3000`。管理端若因此被打开到 Web 端口，或被打开到 Tailscale 没发布的管理端口，实例请求会一直挂起，标志就不消失。

管理员密码已经轮换。过期的管理端会话可能加重这个现象，但重新登录只是核对步骤，不是修复。

方案：

- 先记录点击后的实际 URL、状态码和 `/api/instances/` 是否返回。未核对前不改端口算法。
- 管理端加载超过固定时间必须离开标志，进入已有失败页，并给出可复制的请求地址。
- 管理端地址使用明确端口，不继承 Web 端口。Tailscale 若没有发布该端口，入口应直接说明不可达，而不是无限转圈。
- 科研「系统管理」继续承担导入和邀请码，不把 God Mode 当作组织管理的必经步骤。

验收：管理端要么进入登录，要么在超时后给出失败原因。两种结果都不再停在标志上。

### 4.4 I26-04 系统集成要不要配

六个连接都是「已停用 / 未配置 / not_configured」，因为 Plane 的连接登记是空的。开发计划已经确认 RAGPortal、WeKnora 和 Synlora 进程可达。进程可达和连接登记不是一件事，所以研究链里选库会失败，而 RAGPortal 自己的上传页仍能看到「器件」。

| 系统        | 本阶段       | 需要登记的信息                     | 以后做什么                                 |
| ----------- | ------------ | ---------------------------------- | ------------------------------------------ |
| RAGPortal   | 要登记       | 基地址、凭证引用名。密钥只留在后端 | 列库、经 BFF 上传、健康检查                |
| WeKnora     | 不单独登记   | 不在页面再保存一把密钥             | 由 RAGPortal 代理；Plane 只保存回填的库 ID |
| Synlora     | 不在这六行里 | 沿用现有智能体开关和 BFF           | 节点分析。不要把它配进 Spec_Agent          |
| SpecLabOS   | 保持停用     | 暂不采集                           | Phase 2 的实验运行和记录沉淀               |
| SmartAccess | 保持停用     | 暂不采集                           | 后续设备预约                               |
| Poly_Agent  | 保持停用     | 暂不采集                           | Phase 2 的 ResearchEngine                  |
| Spec_Agent  | 保持停用     | 暂不采集                           | Phase 2 的垂类插件                         |

方案：

- 集成表增加三态：已连接、本阶段不启用、未登记。未登记只留给 RAGPortal。
- 本轮只补 RAGPortal 的基地址和凭证引用名，并做一次不写业务数据的健康检查。
- 页面说明「凭证只存引用名」保留。不要把六个密钥表单都打开。
- Synlora 不新增一行，避免和 Spec_Agent 配重。

验收：研究链能通过 Plane 列出测试库。SpecLabOS 等四行显示「本阶段不启用」，不再显示成故障。

### 4.5 I26-05 旧流程与项目类型

现场下拉同时有「培养项目（旧流程）」和「平行科研课题」。代码里新建表单的初始值就是 `LEGACY_TRAINING`。旧流程还保留「一名责任人只能有一个进行中培养项目」的限制；`RESEARCH_CHAIN` 才会创建现行研究链，并走小组知识库绑定。

「个人培养（硕博博后）」和「团队科研项目」来自另一字段 `research_type`。它们不决定流程，只描述课题属性。这个判断成立，应保留。

方案：

- 新建只创建 `RESEARCH_CHAIN`。表单去掉研究链类型下拉，不再默认旧流程。
- 项目类型保留两组标签：个人培养（硕、博、博后）和团队科研。标签不改变节点、审批和知识库规则。
- 已有 `LEGACY_TRAINING` 不物理删除。提供一次可重复执行的迁移：补齐对应 Plane Project 与研究链，原阶段记录保留为历史事件。迁移前列出受影响 ID。
- 创建页的说明改为「创建一个平行科研课题，并同时建立对应项目」。删掉「培养项目使用阶段流程；团队课题使用任务、周期和模块推进。」

验收：新表单没有旧流程选项。同一个人可以有多个进行中的平行课题。旧记录迁移后仍能打开历史。

### 4.6 I26-06 节点、Tab 与快照

课题页 Tab 是 `overview / nodes / reports / experiments / references / members`，范围是整条课题。节点卡片上的「记录与知识库、报告与成果、实验记录、打开智能体」会切到同一批 Tab，没有节点 ID。所以两排控件看起来重复，点进去又分不清对象属于节点还是课题。

节点下方六块「输入、中间产物、人类决策、AI 动作、验证、输出」是材料和事件投影。截图里的「快照」列写着「该阶段暂无已确认快照」。确认快照是节点提交时写入的 `ResearchChainSnapshot`，不是用户另找入口上传的文件。当前节点还是草稿，所以快照为空是符合模型的，但界面没有把这件事说出来。

成员属于课题，这个判断保留。报告、实验和外部引用也以课题为归属，同时记录可选的来源节点。它们不是节点的私有副本。

目标结构：

| 位置     | 保留什么                             | 去掉什么                                       |
| -------- | ------------------------------------ | ---------------------------------------------- |
| 课题级   | 概览、节点、课题资料、成员           | 把报告、实验、外部引用做成与节点并列的四套入口 |
| 节点级   | 开始、提交确认、请智能体分析         | 用同名按钮再跳一次课题 Tab                     |
| 课题资料 | 按节点筛选的资料、实验记录、外部引用 | 在节点和课题各放一份列表                       |
| 快照列   | 提交确认后的版本、时间和来源         | 手工「新建快照」                               |

空快照写明：「提交并确认本节点后生成版本，不能单独上传。」六块材料在没有事件时写「还没有记录」，不把它们叫成损坏的快照。

验收：从节点不能再打开一个和课题 Tab 内容完全相同、却好像属于该节点的页面。提交确认后，快照列出现一条带版本的记录。

### 4.7 I26-07 报告与成果的文件

「报告与成果」现在是成果著录：名称、期刊或授予单位、DOI、类型。附件上传代码要等已经存在一条草稿成果才出现，空列表里看不到文件入口。周期报告另有附件区，截图里已经能挂 PDF。课题级的开题、总结 PDF/Markdown 两边都不是。

三件事分开：

1. **周期报告**：周报、月报。正文和附件都在报告卡上。
2. **课题资料**：属于整条课题，可选择来源节点。直接上传 PDF 或 Markdown，不先填期刊。
3. **成果著录**：论文、专利等元数据。文件是该成果的可选附件，提交后锁定。

方案只补课题资料入口和成果空态上的两个动作：「上传课题资料」「登记成果」。不把实验原始数据放进这个入口。上传仍走现有 `FileAsset`，类型只允许 PDF 和 Markdown，大小沿用平台配置。

验收：空的报告页可以上传一份 PDF 和一份 Markdown，刷新后还在，并显示关联课题。没有成果行时，不再只剩一个期刊表单。

### 4.8 I26-08 实验记录

人工实验记录的模型、列表和详情已经存在，内容是方法、结果和外部资产引用。SpecLabOS 的运行下发、回调和自动记录在 Phase 2 计划的任务 2.2，不在本轮实现。

当前空白主要是入口和说明：节点按钮把人带到课题级空列表，空列表又没有解释为什么不能从实验系统拉取。

方案：

- 空态写明本阶段可以新建人工记录；SpecLabOS 未启用，不能同步运行记录。
- 「实验记录」打开带当前节点筛选的人工记录列表，并提供新建。
- 不增加原始数据上传。外部资产只保存引用。
- Phase 2 再把运行记录挂到同一条人工记录上，不另起一种实验对象。

### 4.9 I26-09 外部引用与已有器件库

小组绑定在 `ensure_group_knowledge_binding` 中创建，初始状态就是 `PENDING_ADMIN`，直到管理员回填外部库 ID。RAGPortal 下拉里的「器件」没有参与这个匹配。文案「管理员完成该小组的一次手工建库并回填」把「库已存在但未绑定」说成了「库还没建」。

人工测试计划另外规定：只使用 `plane测试`，不得绑定其他库，同一小组的课题复用已确认绑定。因此本轮不能把生产「器件」库自动标成 `READY`。

方案：

- Plane 登记 RAGPortal 后，绑定面板列出候选，并给出匹配理由，例如规范化名称相同。
- 测试工作区只有名为 `plane测试` 的候选可以确认。其他库显示「可见，但本阶段不允许绑定」。
- 确认仍是一次人工动作，并复用现有「一个外部库不能属于两个小组」检查。
- 同一小组后续课题直接复用该绑定，不再各自申请。
- 生产环境以后可以按名称给出建议，但仍需确认。名称相似永远不能单独通过门禁。

验收：器件小组课题不再提示「请先手工建库」。测试环境确认 `plane测试` 后状态变为可上传；「器件」生产库的文档数量不因本次测试变化。

### 4.10 I26-10 工作项选项点不中

创建弹层和属性栏里，状态、优先级菜单已经打开，截图可见 Backlog、Todo、Urgent 等选项。用户点选项没有选中。开始日期和截止日期可用，因为它们不是这套弹层列表。这是选择没有提交，不是选项数据为空。现象曾修好又出现，所以要当作回归，而不是再调一次样式。

方案：

- 在创建工作项弹层和详情属性栏复现状态、优先级、负责人、标签、父项。
- 选项按下时先提交值，再允许外层弹层关闭。菜单可以画到卡片外，但命中区域必须属于列表，不能落在遮罩上。
- 为创建弹层补一条回归：打开菜单、选择 In Progress、保存后详情仍是该状态。日期控件不改。

验收：五个列表字段都能选中并保存。100% 缩放下菜单超出卡片时仍可选。

### 4.11 I26-11 周报正文重复并显示 Connection lost

「打开正文」离开报告卡，进入 Plane 协作页面。截图同时有 `Connection lost` 和不断重复的 `##test`。协作断开时，`usePageFallback` 会取当前文档或 HTML，调用 `setProviderDocument` 后再把结果写回。写回更新了 `description_html`，效果又会再跑；自动保存也在跑。提供器若是合并而不是替换，每一轮都会把已有段落再追加一次。

报告卡上的「已提交」走的是报告状态接口，不走协作页保存。所以会出现「正文在涨，但提交状态看起来没跟上」的错觉。两套状态必须分开显示。

方案：

- 回退路径改为替换整篇文档。写入前比较内容摘要，相同则不请求。自身保存造成的 HTML 变化不得再次触发回退。
- 连接断开时停止后台改写，改为只读预览加一次明确的「保存正文」。重连后先比较服务端版本，不自动合并出重复段。
- 报告卡直接渲染 Markdown。`##test` 显示为标题。`打开正文` 降为次要动作，只在需要协作编辑时进入。
- 正文同步失败不改变报告的草稿、已提交或已退回。提交按钮仍只调用报告提交接口。

验收：断开协作连接后连续等待 30 秒，`##test` 仍只有一段。刷新和重新打开不增加段落。提交后的状态与正文保存结果分别可见。

### 4.12 I26-12 总览人名与行数

刘俊扬在公共工作区看到的科研摘要是单行轮播，「1/2」只显示 `QZX-TEST2`，没有学生名。当前实现用一个当前课题索引轮播，卡片标题是课题名。导师、方向负责人和主 PI 看到的许多课题都不是自己创建的，缺人名就无法扫读。

这不是权限放宽。只改已经通过 ACL 的条目。

方案：

- 查看者不是课题所有者时，标题旁显示所有者姓名。学生看自己的课题不重复写自己的名字。
- 学生最多一行，行内横向切换。
- 直接导师、基础研究负责人、产业化负责人、主 PI 以及其他有下级范围的身份最多五行，行内仍可横向切换。不足五行不补空行。
- 课题摘要使用同一规则，放在科研摘要和跨组件待办之间，不新造第三套卡片。
- 行数由身份能力决定，不写死姓名。

验收：刘俊扬看到邱智鑫的课题时有学生名，两题以内按实际数量展示，布局能力允许到五行。邱智鑫自己的总览仍是一行，且不出现另一名学生的课题。

### 4.13 I26-13 基础研究与产业化的层级

权限继承使用祖先 `path` 的前缀。现在 21 个小组都直接挂在 π-Lab 下面，`business_category` 只是小组字段。`prepare_phase15_role_validation` 又创建了「Phase 1.5 基础研究验证单元」和产业化对应单元：类型是 `TEAM`，父节点为空，`path` 只有自己。组织树因此在 π-Lab 根节点旁边出现层级 0 的小组。负责人挂在这个悬空节点上，管不到器件、类脑计算或磷酸。

现场给出的编制与现有 `TEAM_BUSINESS_CATEGORIES` 相比，只有「测试」不同：代码把测试标成产业化，现场要求归入基础研究。其余 20 个小组一致。以现场编制为准。

目标树：

```text
π-Lab
├── 基础研究
│   ├── 类脑计算、原子智能、器件、多肽、测试、量子
│   ├── 自旋与超快、AI决策、逻辑、控制
│   └── 跨尺度表征、生命、超分子材料
└── 产业化
    └── 磷酸、金属化、光刻胶、电氢联储、转移胶、硅基、电池、华为
```

方案：

- 在 π-Lab 下新增两个 `LAB` 节点：基础研究和产业化。不新增枚举。
- 按上表重挂 21 个小组，重算 `path` 和 `depth`。小组的业务分类改由方向节点决定，测试改为 `BASIC_RESEARCH`。
- 两位方向负责人改挂到对应 `LAB`，角色使用现有 `OWNER`。继承继续只用 `path`，不另写一套方向权限。
- 两个 Phase 1.5 验证单元在确认没有课题、成员以外的业务数据后停用。负责人成员关系迁走，不留第二个根。
- 组织树只渲染一个根。父节点为空且类型不是根的数据视为异常，不排到根前面。
- 基线计数从「1 个根 + 21 个小组 = 22」改为「1 个根 + 2 个方向 + 21 个小组 = 24」。学生 189、导师 14、唯一主 PI 不变。同步修改 `--verify-only` 和基线文档。
- `nearest_team` 仍向上找到 `TEAM`，小组知识库不改挂到方向节点。

验收：基础研究负责人能看到器件等 13 个小组的继承范围，看不到磷酸等产业化小组。反向同样成立。组织树不再出现层级 0 的验证单元。验证命令期望 24 个节点。

## 7. 风险与不做的事
