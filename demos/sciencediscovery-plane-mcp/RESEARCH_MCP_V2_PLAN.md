# 科研链 MCP v2 开发计划：Agent 受控操作

计划编写日期：2026-10-17。本文保留当时的分期设计；后续 v2.1 实现与部署状态见 [v2.1 使用说明](RESEARCH_MCP_V21.md)。v2.2/v2.3 尚未实施。

## 1. v1 是否已完成，可以进入下一步吗

**可以。以“本地 Plane + Codex 通过 MCP 读取授权科研链、节点与已支持内容”为口径，v1 已基本完成，适合作为 v2 的开发基线。** 不能将此结论扩大成全部文档全文、外部来源及所有 Agent 平台均已验收。

依据：[核心能力说明](RESEARCH_MCP.md)、[验收摘要](../../docs/operations/research-mcp-v21-acceptance.md)。最近一轮后端 79 项、独立代理 5 项、真实 REST/HTTP MCP 71 项通过；Codex 三轮执行 21 次真实 MCP 调用，包含正常读取及预期越权/正文拒绝。调用前后 18 张业务表的数据快照一致。上述数字来自既有验收，本轮没有重新运行。

| 能力                                                      | 当前状态                            | 对 v2 的影响                                         |
| --------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------- |
| 链、节点、事件、快照、科研任务、任务评论                  | 已实现并完成本地读取验收            | 直接复用为写入前上下文与写入后读回通道               |
| 分析、实验、正式报告等已支持资源正文                      | 已支持有界读取、版本/游标与权限检查 | 可以引用实际读到的内容，不能推断未读取全文           |
| 论文稿件评审、阶段材料、课题附件、外部引用                | 元数据已验收                        | 可以按权限引用对象；正文解析作为独立后续任务         |
| Agent 公开事件                                            | 公开投影正文已验收                  | 可读公开回答与溯源信息，不暴露内部推理及原始工具结果 |
| ScienceDiscovery 自动装配                                 | 有实现代码，未做本轮端到端验收      | v2 先用本地 Plane + Codex；不能宣称远端接入已通过    |
| Synlora 自动装配、外部源端实时 ACL/同步、真实附件上传解析 | 尚未完成对应闭环                    | 分别立项，不阻塞授权范围内的任务、草稿写入           |

其中 `paper_review` 指论文稿件评审，不代表文献条目或文献阅读笔记已经覆盖。v1 本地功能通过也不等于已完成生产容量或真实科研流程验收。

## 2. v2 的业务目标与分期

目标：用户向 Agent 下达科研协作指令后，Agent 能读取当前证据，形成明确的变更提案，在授权范围内写入 Plane，再返回真实对象 ID、状态及读回结果。

### v2.1：先交付任务协作与分析草稿

推荐第一批只做以下五种操作：

| 操作 action            | 落库结果                     | 限制                                                                                   |
| ---------------------- | ---------------------------- | -------------------------------------------------------------------------------------- |
| `create_task`          | 当前节点新增科研任务         | 首批不指派、不设截止时间，状态为 `DRAFT`；仍要求现有任务管理权限                       |
| `append_task_comment`  | 指定科研任务追加评论         | 追加留痕，不覆盖他人评论；按现有任务可见性和评论权限校验                               |
| `save_analysis_draft`  | 保存新的分析草稿             | 强制 `DRAFT`，携带依据；不接受模型通过 `confirmed=true` 转正式                         |
| `attach_task_resource` | 给允许修改的任务绑定已有资源 | 首批只允许当前无绑定的任务；资源类型限现有任务模型支持枚举；同时检查来源权限和节点范围 |
| `append_research_note` | 节点新增科研过程记录         | 使用服务端固定事件类型 `RESEARCH_NOTE`，标明 Agent 来源；不允许模型指定任意事件类型    |

这里的任务与评论是二开 `ResearchChainNodeTask` / `ResearchTaskComment`，不复用原生 Issue 评论来替代科研任务评论。保存分析草稿是新增版本候选，不悄悄覆盖既有正式分析。

首批不提供既有任务任意编辑、重新绑定已有资源或批量覆盖。任务分派、期限与状态进入后续阶段，避免第一版同时改变协作责任和研究结论。

### v2.2：创建节点与科研迭代

- 在既有科研链中创建 `DRAFT` 节点，可提交标题、受支持的节点类型及说明。
- 支持基于同链已有节点创建下一轮迭代，校验 `parent_node_id` 与 `loop_iteration`。
- 根节点使用 `loop_iteration=0`；迭代子节点使用 `loop_iteration>=1`。当前 `parent_node` 是迭代父节点，不应包装成任意依赖边或通用 DAG 编辑能力。
- 创建节点需要明确的链级写授权；仅有单节点授权的 Agent 不能借此创建兄弟节点或扩展授权范围。
- “在已有项目下新建科研链”列为可选扩展，需要项目级独立授权；不包含新建项目、成员或组织权限。

### v2.3：受控推进协作与节点流程

- 增加任务分派、期限调整和任务提交；复用现有可指派人员范围与任务状态机。
- 节点先开放 `START`、`SUBMIT_REVIEW` 两类动作，复用现有节点状态机。
- 从分析草稿形成正式分析或不可变快照，需要独立的人类确认、明确内容与来源版本；模型不能自行把草稿“确认”为科学事实。
- 任务验收、节点 `APPROVE` / `RETURN` 等决策继续由具备角色权限的人在 Plane 操作；以后如需 Agent 代执行，再单独开放精确授权。

当前节点流程为 `DRAFT → ACTIVE → WAITING_HUMAN → COMPLETED`，退回进入 `NEEDS_REVISION`。不能直接写状态字段绕过合法动作。**科研任务完成不会自动导致节点完成。**

v2 默认范围不含删除/归档科研链、删除节点、成员与 ACL 修改、覆盖不可变快照、设备控制、直接执行实验或无边界外部访问。

## 3. 交互：先看清变更，再执行并读回

建议采用服务端持久化提案，而不是只给 MCP 加几个直接写库工具。

```text
用户业务指令
  → v1 读取链/节点/证据
  → Agent 准备结构化操作提案
  → Plane 展示目标、内容、依据和影响
  → 用户确认该提案或命中预先配置的有限授权
  → Agent 执行同一个 operation_id
  → 业务服务写入 + 事件 + 审计
  → v1 读回真实对象，返回结果
```

准备提案会新增提案记录，但不会创建任务、评论等目标业务对象。提案一旦生成，其动作、目标与载荷不可修改；需要修改时创建新提案，旧提案取消或到期。

默认采用 Plane 内确认。同一请求生成的几个操作可在同一页面集中审阅，但首版逐项显示执行结果，不承诺跨操作全有或全无；执行失败后不自动删除已经成功的评论或任务。以后如需原子批次，应另设服务端批次契约。

低影响操作可在后续开放有限预授权，例如“当前节点仅追加评论，24 小时内最多 10 次”。必须由用户事先在可信入口设置范围、动作、有效期和次数，不能由 Agent 自行生成授权。首批默认不依赖该扩展。

**模型传入 `approved=true`、聊天里引用一段“同意”或 MCP 的 `readOnlyHint`，都不能替代服务端授权记录。** 现有原生任务进展 Demo 的本地确认标记、远端工具审批接口，不等于已经具备科研操作提案审批能力；需要补齐本方案的可信确认入口。

## 4. MCP 工具契约

保留 v1 的十个工具及现有只读入口，新增显式启用的写操作入口/模式。建议新增以下五个工具，业务动作由严格枚举的 `action` 区分：

| 工具                         | 用途                                         | 核心参数                                                                                     |
| ---------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `prepare_research_operation` | 校验范围并保存不可变提案，返回预览和审核地址 | `request_id`、`action`、`target`、按 action 区分的 `payload`、`source_refs`、`preconditions` |
| `get_research_operation`     | 查询提案、授权状态、执行结果与冲突           | `operation_id`                                                                               |
| `list_research_operations`   | 列出当前调用方范围内的提案，便于恢复         | 目标过滤、游标、页大小                                                                       |
| `execute_research_operation` | 执行已批准且仍满足权限/前置条件的提案        | `operation_id`；不接收替换后的业务载荷                                                       |
| `cancel_research_operation`  | 取消尚未执行的提案                           | `operation_id`；不能撤销已提交业务数据                                                       |

`prepare` 的 JSON Schema 使用按动作区分的封闭结构，拒绝未知字段、任意 URL、SQL、任意模型名和自由状态设置。workspace、真实用户和授权主体从认证上下文确定；参数中的目标必须与其匹配。

提案至少返回：操作 ID、目标链/节点/任务、规范化后的变更内容、可能的事件/通知、依据 ID 和版本、前置条件、到期时间、审核地址。成功执行至少返回业务对象 ID、状态、事件 ID、审计关联 ID，以及读回状态。

`get/list` 标记只读；`prepare/execute/cancel` 标记非只读，另按实际行为提供工具提示。工具提示仅用于客户端展示，权限检查全部在后端。

不向 Agent 暴露 `approve_research_operation`。确认通过 Plane 已登录用户接口完成，执行时读取数据库中的确认记录。

| `views/chain_foundation.py`、`services/chain_state.py` | 节点、事件、快照与状态机         | 抽出共享变更服务，按阶段开放动作                    |

| `research_client.py`、`research_mcp.py`、`http_mcp.py` | 独立客户端与只读代理             | 新增显式操作模式，保留只读白名单与默认配置          |
| Plane 科研链前端                                       | 链、节点、任务展示               | 新增提案预览、确认/拒绝及执行结果界面               |

以上路径均相对于仓库：后端在 `apps/api/plane/research/`，独立代理在本文所在目录。新增业务服务建议为 `services/agent_operations.py` 及分域 mutation 服务；最终文件划分以避免重复业务规则为准。

MCP 调用共享服务，不伪造网页 Request 去调用 DRF 视图，也不复制另一套状态机。网页继续调用同一服务，避免两个入口对权限或并发作出不同判断。

数据库初步新增：

- `ResearchAgentOperation`：不可变动作载荷、哈希、目标、提出用户/Agent、原始授权边界、依据与前置条件、有效期、状态、幂等键、真实执行结果及读回状态。
- `ResearchAgentOperationApproval`：审核用户、精确提案哈希、审核决定、时间和到期时间。执行时与提案一起校验和消费，防止一次批准被替换内容或重复执行。

操作状态可采用 `PROPOSED / APPROVED / COMMITTED / REJECTED / CANCELLED / EXPIRED / CONFLICT`。读回状态单列，区分“已提交但读回待确认”和“未写入”；事务失败不将提案误记为成功。数据库迁移使用当前分支的下一个可用编号，不修改已执行的历史迁移。

## 6. 写入必须保证的行为

### 权限与身份

有效写权限取以下交集：功能开关、工作区策略、当前用户业务权限、凭据写能力、授权动作、授权目标、有效确认记录。v1 grant 不自动升级为写 grant，普通个人 Key 可读也不表示已获写授权。

批准不借用审核人的更高权限替代执行主体权限。要允许委托行为，必须另有明确的委托契约。执行前以及事务内重新检查成员、授权、链状态和资源 ACL，过期、撤销、归档、删除均拒绝写入。批准、撤销与执行使用一致的锁顺序和事务边界，明确先后结果。

操作记录及结果查询也受当前权限限制；幂等重放不能绕过已经撤销的资源访问权限。Grant 到期不自动续期；更换凭据恢复同一操作时，必须重新认证同一用户并覆盖原目标、动作范围，不继承旧凭据的额外权限。

### 幂等、并发与失败恢复

- 相同主体、目标、动作及 `request_id` 的相同载荷返回同一操作；更换载荷返回冲突。业务层幂等键由服务端从操作 ID 稳定派生。
- 执行锁定操作与目标记录；同一操作并发执行只产生一次业务效果。业务对象、操作结果、事件和审计在同一数据库事务内提交。
- 可变目标使用锁内检查的完整业务前置条件哈希，或补充统一维护的修订号；所有相关网页写路径也必须纳入该机制。v1 截断后的展示哈希不能直接作为写入并发控制依据。
- 提案依据发生内容变化、权限撤销、状态变化，或资源已有绑定，返回明确冲突，重新准备提案；不能自动放宽条件继续写。
- 写入后响应超时，查询并恢复同一个 `operation_id`，不能换新 `request_id` 盲目重建。已提交但读回失败标为待确认，后续只补读回。
- 数据库锁按统一顺序获取。通知等外部副作用在提交后调度，不能因重试执行重复发送；进入分派阶段时补齐通知幂等/可靠投递。

### 来源、内容和事件

资源必须同时满足当前用户可读、在授权范围内、属于允许的关联类型、版本有效。节点关联不赋予来源访问权；不得因 Agent 传入 ID 就直接绑定。

评论/说明按现有格式规则清理并限制长度；外部内容中的指令只能作为资料，不能更改工具权限或批准提案。审计保存摘要、目标及哈希，不写令牌或原始私密工具输出。

记录实际用户与 Agent 标识，可选关联 session/run；独立 Codex 无远端会话时使用服务端连接/调用关联 ID，不伪造远端运行。`source_refs` 区分“读到正文”与“仅有元数据”。创建/提交等事件由业务服务生成，Agent 不得自行生成 `VALIDATION_PASSED` 或冒充 `HUMAN_DECISION`。

## 7. 兼容与开放方式

- 保留 `RESEARCH_MCP_ENABLED` 的既有读开关；新增独立写开关，例如 `RESEARCH_MCP_WRITE_ENABLED`，默认关闭。
- 旧 `research-read-only` 模式始终只有原来的十个读工具；新增操作模式仅向获授权凭据公开对应工具和动作。
- 当前独立代理有只读工具白名单，ScienceDiscovery 装配也有工具目录校验；须显式区分版本与模式，不能往旧目录直接加入写工具导致旧连接失效。
- 首次接入目标是本地 Plane + Codex，支持明确配置的 HTTP 或 STDIO 入口，不要求启动 ScienceDiscovery。
- ScienceDiscovery / Synlora 的写授权分发、会话绑定、审批交互和端到端验证作为后续平台适配；协议可复用，不把未经验证的平台写接入列为本次交付。

## 8. 开发顺序与交付物

| 顺序 | 工作包                                   | 完成标志                                                                  |
| ---- | ---------------------------------------- | ------------------------------------------------------------------------- |
| 1    | 冻结 v1 基线与 v2.1 五种动作契约         | 记录 v1 验收、迁移和配置；确定目标/字段/权限/错误，不扩大动作范围         |
| 2    | 抽出共享任务评论、分析草稿和过程记录服务 | 网页与 MCP 使用同一业务规则；既有流程兼容                                 |
| 3    | 提案模型、确认记录、写 grant、并发与幂等 | 替换载荷、重复执行、超时恢复和过期/撤销均有确定行为                       |
| 4    | 五个 MCP 工具及独立操作模式              | Agent 可准备、查询、执行和恢复；旧只读入口保持兼容                        |
| 5    | Plane 提案审核及结果展示                 | 用户能看到确切变更、批准/拒绝，查看真实执行对象；不强制每个子操作单独跳页 |
| 6    | v2.1 本地 Plane + Codex 验收             | 五种动作闭环和权限/并发/失败用例通过，形成证据报告                        |
| 7    | v2.2 节点与迭代能力                      | 链级授权下创建草稿节点，单节点授权不能扩张                                |

建议将 1—6 作为下一次独立交付，再推进 7—8。工程量粗估：熟悉仓库的开发者完成 v2.1 约 **8—12 人日**，v2.2 约 **3—5 人日**，v2.3 约 **4—6 人日**；属于规划估算，不是工期承诺。若同时加入新建科研链、正文解析、原子批次、预授权或远端平台适配，需另估。

## 9. 验收计划

继续采用本地 Plane + Codex 的方式，不以 ScienceDiscovery 启动或调用作为本阶段前提。使用人工构造的独立测试工作区，不要求用户先上传科研材料。

| 类别       | 必须验证的结果                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------------- |
| 正向闭环   | Agent 真实 MCP 读取 → 准备 → 用户确认 → 执行 → v1 读回；目标任务/评论/草稿/记录确实落到对应链和节点 |
| 未确认     | 只准备、拒绝或到期时，提案可以有记录，目标业务表没有新增或变更                                      |
| 权限       | 只读 Key/grant、跨节点/链/工作区、只评审角色、撤销成员、来源无权均不能越权写                        |
| 审批真实性 | Agent 自报同意、替换载荷、别人的审批、过期审批和越权审核不能完成写入                                |
| 来源       | metadata-only 资源不能被声称已全文阅读；不可读引用不能绑定；来源版本变化触发冲突                    |
| 幂等与恢复 | 同一操作重复、并发执行、提交后响应丢失只产生一份结果；可查询并恢复同一操作                          |
| 竞争修改   | 网页修改、链归档/节点删除、资源重新绑定、撤销与执行竞争均得到确定结果                               |
| 副作用     | 事件、审计、通知可溯源，不冒充人工决策，不泄露凭据，不产生重复通知                                  |
| 业务语义   | 分析仍为草稿；任务完成不改变节点状态；仅有节点 grant 不能创建新节点                                 |
| 兼容       | v1 十工具及既有只读客户端继续工作；写开关关闭后不暴露可执行写能力                                   |

后端补齐共享服务单元测试、提案契约测试、真实 API/MCP 验收；前端验证预览内容与实际执行一致。保留操作 ID、真实对象 ID、前后状态和脱敏调用记录，不以模型口头声称成功代替落库证据。

遵循仓库限制：不运行 `docker-compose-test.yml`，不自行构建 Docker 测试镜像。测试需使用隔离数据库/缓存；实际部署和验收按后续授权执行。本文不是已执行的 v2 验收报告。

## 10. 业务场景与交付效果

### 场景 A：从现有分析中拆出待办

用户：“根据当前容量衰减分析，把还没核实的条件整理成三条任务，并存一版分析草稿。”

v2.1：Agent 读取分析及节点上下文，准备“核对温度、核对倍率、核对样品负载量”三条未指派任务和一份带依据的分析草稿。用户集中审阅后，执行结果返回三个任务 ID 和一个草稿 ID，逐项可读回；节点仍处于原状态，不自动形成验收结论。

### 场景 B：把核查进展留在科研任务里

用户：“在温度核查任务下补充：已核对记录，设备日志还没找到；把已有阶段材料关联上。”

v2.1：新增科研任务评论；若该任务尚未绑定资源，且材料可读、类型受支持、范围正确，再执行绑定。用户可在 Plane 查到评论与依据。若已有绑定或材料无权，绑定操作明确冲突或拒绝，不覆盖旧关联，也不影响已经成功的独立评论操作。

### 场景 C：建议第二轮科研迭代

用户：“第一轮结果不足，建立第二轮实验设计节点，沿用第一轮作为迭代来源。”

v2.2：在获得链级写授权且用户确认后，创建同链 `DRAFT` 子节点并保存合法迭代关系。只有当前节点授权时明确拒绝创建。此时只是形成工作结构，没有启动实验、调用设备或认定实验成功。

### 场景 D：整理完成后送审

用户：“把当前节点准备好的结果提交给导师审核。”

v2.3：校验节点状态、角色和确认记录，通过合法 `SUBMIT_REVIEW` 动作进入 `WAITING_HUMAN`；导师在 Plane 审核。Agent 返回真实状态和依据，不自行执行 `APPROVE` 将节点置为完成。

最终效果：v1 解决“Agent 能读懂哪些科研上下文”，v2 按上述阶段逐步实现“Agent 能把明确授权的协作动作写回科研链，并且每次操作能查到、能核对、能恢复”。
